# InferOps — Observability Evidence

## Phase 8: Observability

### 1. Purpose

The purpose of this phase is to collect and organize application logs, application metrics, and Kubernetes health information. This evidence will help InferOps identify application problems and support root cause analysis in later phases.

### 2. Application Logs

Application logs record events that occur while the demo application is running.

**Log sources:**
- Application-level logs generated using Python's logging module.
- HTTP request logs generated by Uvicorn.
- Container logs collected from the Kubernetes deployment.

**Validation performed:**
- Checked application startup logs.
- Verified logs for the `/health` endpoint.
- Verified logs for the `/api/data` endpoint.
- Inspected Kubernetes container logs using `kubectl logs`.

**Observed result:** Application startup messages, application events, and HTTP request records were visible in the container logs.

### 3. Application Metrics

The demo application exposes a `/metrics` endpoint that returns request statistics in JSON format.

The metrics include:
- `total_requests`: Number of requests recorded by the application.
- `http_status_counts`: Number of responses grouped by HTTP status code.
- `error_count`: Number of responses with status codes of 400 or higher.
- `error_rate_percent`: Percentage of recorded responses classified as errors.
- `average_response_time_seconds`: Average response time recorded by the middleware.

**Validation performed:**
- Requested the `/metrics` endpoint.
- Generated a successful request to `/api/data`.
- Tested the controlled error endpoint locally.
- Verified metrics from the running Kubernetes application.

**Observed Kubernetes metrics:**

```json
{
  "total_requests": 3,
  "http_status_counts": {
    "200": 3
  },
  "error_count": 0,
  "error_rate_percent": 0.0,
  "average_response_time_seconds": 0.058217
}
```

*Note: This is a sample observation from one test session. Metric values change as requests are processed and reset when the application restarts.*

### 4. Kubernetes Health

Kubernetes health was inspected using `kubectl` commands.

**Commands used:**

```bash
kubectl get pods
kubectl get deployments
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl describe pod inferops-demo-b56687779-tm94l
kubectl get pod inferops-demo-b56687779-tm94l -o wide
```

**Observed result:**
- The demo application Pod was `Running`.
- The Pod was ready: `1/1`.
- The deployment showed `1/1` available replica.
- The Pod had zero restarts during the inspection.
- The inspected events were normal Kubernetes lifecycle events, with no Warning events in the checked output.

### 5. Evidence Summary

| Evidence source | Collection method | Validation result |
|---|---|---|
| Application logs | Python logging and Uvicorn logs | Application events and HTTP requests observed |
| Container logs | `kubectl logs` | Logs retrieved from the Kubernetes deployment |
| Application metrics | `/metrics` endpoint | Request counts, status codes, errors, and response time returned |
| Kubernetes health | `kubectl get`, `describe`, and events | Pod and deployment health inspected |

### 6. Limitations

- Metrics are stored in application memory and reset after a restart.
- The metrics endpoint returns JSON rather than a complete monitoring-system format.
- The current evidence represents individual test sessions, not long-term monitoring.
- No centralized log storage or historical metrics database has been configured in this phase.

### 7. Conclusion

The InferOps demo application produces logs, exposes request metrics, and runs in Kubernetes with its health status inspectable through Kubernetes commands. These observations provide structured evidence for the next stage of the InferOps incident detection and root cause analysis workflow.
